# Threat Model — CRM AI Agent (Этап 0)

Дата: 2026-09-03. Основано на архитектуре из ревью (см. `architecture.md`).

## Активы

- Учётные данные CRM/Webitel/Telegram сервисных аккаунтов.
- PII пользователей CRM (ФИО, телефон, e-mail).
- Целостность CRM-данных (пользователи, статусы заявок).
- Целостность audit trail.
- Доступность и корректность workflow согласования в Telegram.

## Модель нарушителя

| Актор | Возможности | Мотивация |
|---|---|---|
| Автор заявки | Пишет произвольный текст в описание/комментарии CRM | Случайная или намеренная prompt injection, попытка обойти согласование |
| Скомпрометированный Telegram-аккаунт approver | Может отправлять callback от имени approver | Несанкционированное подтверждение опасных действий |
| Внешний наблюдатель логов/трейсов | Читает artifacts, логи | Утечка PII, credentials |
| Сбой инфраструктуры (crash, timeout, сеть) | Непреднамеренный | Неизвестное состояние mutation, дублирование действий |
| Разработчик/оператор системы | Ошибка конфигурации policy | Слишком широкие права действия |

## Ключевые угрозы и меры

| Угроза | Вектор | Мера |
|---|---|---|
| Prompt injection | Текст заявки инструктирует LLM выполнить действие | Текст — untrusted data; LLM возвращает только structured output; Policy Engine не доверяет тексту |
| Подделка согласования | LLM интерпретирует фразу "согласовано" как факт | Согласование подтверждается только `trust_level: crm_workflow_approval`, не текстом |
| Replay Telegram callback | Повторная отправка callback | Атомарный одноразовый переход `PENDING → APPROVED/REJECTED`, TTL |
| Approval не тем человеком | Chat ID/user ID не проверены | Allowlist + role check + chat_id validation на каждый callback |
| Устаревший план выполняется после изменения заявки | Snapshot изменился между approval и execution | `snapshot_hash`/`plan_hash` revalidation перед mutation |
| Повтор mutation после сбоя приводит к дублированию | Автоматический retry после timeout | Mutation не повторяется вслепую; сначала read-only reconciliation |
| Утечка PII/credentials через artifacts | Screenshots/traces содержат чувствительные данные | Redaction rules, ограниченный retention, доступ по ролям |
| LLM галлюцинирует CRM/Webitel ID | LLM формирует план с ID | LLM не возвращает доверенные ID; entity resolution — детерминированный read-only слой |
| Несанкционированное действие вне каталога | Ошибка в Plan Compiler или policy | Action Registry — единственный источник разрешённых действий; hard-deny для незарегистрированных |
| CAPTCHA/MFA обход | Автоматизация пытается обойти защиту входа | Явный запрет; переход в `MANUAL_REVIEW` |

## Остаточные риски (требуют решения владельца проекта)

- Если в CRM нет структурированного поля согласования (см. `open_questions.md`, вопрос 3), MVP не может автоматически проверять approval — потребуется либо ручной ввод, либо `MANUAL_REVIEW` для всех заявок.
- Компрометация Telegram-аккаунта единственного approver остаётся риском до введения правила "четырёх глаз" для high-risk действий.
